# Min-Maxスケーリング実験レポート(`run_20260827_014318`)

設計・実装の詳細は[lattice_fork_minmax_5gen_experiment.md](lattice_fork_minmax_5gen_experiment.md)を参照。本レポートは実際に5世代を実行した結果をまとめる。

**このレポートは`llm_gp/report.py`のバグ修正後に書き直したものです。** 修正前の版では実験全体の最良個体を`ind_000032`(世代3生まれ)と結論していましたが、これは誤りでした。詳細は下記「レポート自体のバグとその修正」を参照。

## 目的(再掲)

fitnessの正規化を、固定基準値(`planning_reference`等)との比較から、**その世代で実際に成功した個体群のmin/max**を使った相対スケーリングに変更し(`llm_gp/fitness.py`の`GenerationMetricStats`)、意図通りに機能するかを確認する。

## 実験設定

- Config: `config/ros_gazebo_lattice_fork_minmax_5gen.yaml`
- マップ: lattice_fork(`ros_gazebo_lattice_fork_5gen.yaml`と同一)
- 集団構成: 単一集団10個体(島なし)、2ペア×3個体=6個体/世代、5世代
- 評価: `repetitions_per_goal: 3`、ゴールは`goal_x_range=[15.0,16.5]`/`goal_y_range=[1.5,2.3]`からランダムサンプリング

## 実行環境の問題と対応(概要)

本実験は実行開始から完走まで、コードとは無関係な2つの環境要因でつまずいた。

1. `scripts/run_ros_gazebo_evaluation.sh`がCRLF化+関数欠落しており全個体が評価失敗 → `git checkout`+LF化+`.gitattributes`追加で解消。
2. Gazeboの実時間係数が6〜16%まで低下し全個体がタイムアウト → 電源プラン/Defender除外/WSL再起動などを試したが改善せず、最終的に**`wsl --update`によるWSLカーネル更新(6.6.114.1-1 → 6.18.33.2-2)で解消**(実時間係数がほぼ1.0まで回復)。

## レポート自体のバグとその修正(本レポートの中心的な訂正内容)

`llm_gp/report.py`は各個体の適応度をDBの`evaluations.fitness`列から読んでいたが、この列は**その個体が最後に「親候補」として再採点された時点の値**しか保持していない。Min-Maxスケーリングでは個体が生存し続ける限り毎世代再採点されるため(`EvolutionEngine._score_individuals`)、ある世代の行に表示される適応度が、実際にはその世代より**後の世代で上書きされた値**になっているケースがあった。

例えば旧レポートは「世代3で生まれた`ind_000032`の適応度は0.9002」としていたが、これは`ind_000032`が世代5まで生存し続けて再採点された**最終値**であり、世代3で生まれた瞬間の本来の値は0.8941だった。同様に世代0の初期基準個体も、生存し続けた個体は後の世代の値に汚染されており、**旧レポートが初期基準個体として使っていた`ind_000009`(適応度0.7640相当として扱われていた)は、実は初期集団の中で最良の個体ではなかった**。

修正版(`llm_gp/report.py`)は、各世代ごとに実際のスコアリングプール(その世代に入ってくる親の集団+その世代で新規に生まれた子)を再構築し、その場でfitnessを再計算して表示するようにした。これにより初期集団・各世代の値が全て本来の値に訂正されている。

## 訂正後の結論:実験全体の最良個体は`ind_000008`(初期個体、無変更)

修正後に判明した最も重要な事実:

- **初期集団(世代0)の中で最も適応度が高かったのは`ind_000009`ではなく`ind_000008`(適応度0.9492)だった。**
- **`ind_000008`は5世代を通じて一度も誰にも上回られておらず、実験全体の最良個体もこの`ind_000008`のままだった。**
- 世代3で生まれた`ind_000032`(訂正後の適応度は世代3時点で0.8941、世代5時点の最終値で0.9002)は、5世代を通じて最も高い適応度を記録した**新規個体**ではあるが、`ind_000008`(0.9492)には最後まで届いていない。

初期集団10体は全て同一のベースラインコード(ヒューリスティック重み1.0、無変更)のコピーであり、ゴール位置のランダムサンプリングと評価ノイズだけで適応度が0.14〜0.95まで分布することは以前から確認していた。今回の結果は、**そのノイズの大きさが、5世代・単一集団10個体という規模のGP探索で得られた改善を上回ってしまった**ことを意味する。

## `ind_000032`(5世代を通じた新規個体の最良)のコード変更

参考として、新規に生まれた個体の中では最良だった`ind_000032`(世代3生まれ、演算`mutation_only`、親`ind_000005`)の変更内容を記録しておく。

```diff
-constexpr float kLlmGpHeuristicWeight = 1.00000000f;
+constexpr float kLlmGpHeuristicWeight = 1.08192050f;
```
```diff
-RIndex(next_i, potential[next_i] + distance * neutral_cost_ * tBreak * kLlmGpHeuristicWeight));
+RIndex(next_i, potential[next_i] + distance * neutral_cost_ * tBreak * kLlmGpHeuristicWeight * 0.9f));
```

正味の係数は`1.08192050 × 0.9 ≈ 0.9737`で、ベースライン(1.0)よりわずかにヒューリスティックの効きを弱める方向の変更。OpenAI gpt-4o-miniによる変異は2回ともmeaningful-changeゲートに拒否され、決定論的フォールバック(ヒューリスティック重みのジッター)で採用された。

## 10回再評価による統計的検証について(要注意)

GP実行直後に自動実行された`--verify-repetitions 10`の検証は、**`ind_000009`(誤って初期基準個体として選ばれていた個体)と`ind_000032`を比較したもの**であり、本来比較すべき`ind_000008`との比較にはなっていない。

| 指標 | `ind_000009`平均 | `ind_000032`平均 | 改善率 | p値 | 有意? |
|---|---:|---:|---:|---:|:---:|
| path_length | 39.44 | 37.86 | +4.02% | 0.0005 | True |
| arrival_time | 174.81 | 169.21 | +3.20% | 0.0027 | True |
| node_expansions | 43193.5 | 50919.7 | -17.89%(悪化) | 0.0018 | True(悪化方向) |

`ind_000032`が`ind_000009`より優れているという結論自体はこの検証の範囲では正しいが、**「実験全体の最良個体」との比較にはなっていない**。`ind_000008`と`ind_000032`(あるいは`ind_000008`と初期集団平均)を正しく10回比較するには、追加のGazebo評価が必要(未実施)。

## 結論

- Min-Maxスケーリング方式のfitness計算自体(`llm_gp/fitness.py`)は設計通りに機能しており、コード側の実装に問題は見つかっていない。
- 一方で**分析・レポート側(`llm_gp/report.py`)に、再採点によって上書きされた適応度を古い世代の行にそのまま表示してしまうバグがあった**。これを修正した結果、「5世代で意味のある改善が得られた」という当初の結論は誤りで、正しくは「**初期集団の中の1個体(`ind_000008`)を最後まで誰も上回れなかった**」という結果だった。
- 単一集団10個体・5世代という規模では、評価ノイズ(同一コードでも適応度が0.14〜0.95まで振れる)がGP探索による改善効果を上回ってしまう可能性が高いことが、今回のバグ修正によって図らずも定量的に裏付けられた。実験規模を大きくする(個体数を増やす、`repetitions_per_goal`を増やしてノイズを抑える)か、fitnessの重み付けを見直すことが今後の検討事項になる。
- Min-Maxスケーリングと固定reference方式のどちらが優れているかを定量的に比較するには、同一シード・同一世代数での並行実行、かつ今回発覚したレポートのバグを踏まえた正しい集計が必要。
